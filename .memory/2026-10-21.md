## 新功能：连接监控（进行中）

### 性能实测结论（Apple M4 / darwin arm64）

| 项 | 数据 |
| --- | --- |
| 管道加字节计数 | 5.60 → 5.53 GB/s，差异在噪声内（多轮出现反向结果） |
| 真实 SSH 通道吞吐 | 1.86 GB/s，加计数后无变化 |
| 连接登记（无竞争 / 32 路争用） | 21.7 ns / 200 ns |
| 1Hz 采样 500 条 | 646 ns |
| JSON 序列化 500 行 | 107 µs |
| 单条记录内存 | 136 B 结构体 + 字符串 ≈ 240 B |
| macOS 进程表全量扫描 | **1.5 ms**（157 个 socket） |

结论：吞吐无影响（`io.Copy` 在 SSH 通道上本来就走通用拷贝，没有 splice/sendfile 快路径可丢）。真正的瓶颈是 SSH 加密本身（−67%）。1.5ms 的进程扫描**必须异步**，放 accept 路径上 1000 连接/秒就要 1.5 秒 CPU。

### 设计决策

- **已关闭连接保留 5 秒 + 最多 200 条**（时间/数量双上限）。理由不是"短连接多"，而是：行抖动会让"断开"按钮点不中；断开瞬间才是信息量最大的时刻（RST/拒绝/超时）；主动断开需要视觉反馈。
- 一条 Entry = 一个客户端 socket。`-D` 的 HTTP keep-alive 下同一 socket 换目标时以最后一次为准。
- 计数在数据真正流经处包装，不在 socket 上统一包装——`-D` 的 bufio 会先把头读进缓冲再原样写出，统一包装会把请求头计两次。
- 登记上限（4096）只是"不再显示"，绝不淘汰活跃连接。
- 进程列只在客户端在本机时查（`-L`/`-D`）；`-R` 的发起方在远端，只显示来源 IP。

### 新增文件

- `internal/conn/`：Entry（计数/状态/Kill）+ Registry（采样/淘汰/作用域断开）
- `internal/proc/`：按本地端口反查进程。Windows `GetExtendedTcpTable`、Linux `/proc/net/tcp` + `/proc/*/fd`、macOS libproc cgo
- `frontend/src/views/Connections.vue`：虚拟滚动表格

### 「活跃连接数」的口径与验证

一条记录 = 一个 TCP socket，不是一次页面访问、也不是一个 HTTP 请求。浏览器对同一个
host:port 的 HTTP/1.1 并发连接上限是 6，加上 WebSocket/长轮询会超过 6，所以打开一个
SPA 看到 6~7 条活跃连接是正常的。

已加回归测试 `internal/tunnel/conn_count_test.go`：并发开 7 条 keep-alive 长连接穿过
隧道，断言「界面活跃数 == lsof 数到的 ESTABLISHED socket 数」，再关 3 条断言变成 4。
实测 7/7、4/4 完全一致，说明计数没有重复也没有漏。

注意：`lsof -iTCP:PORT` 会把连接两端各列一行，数的时候必须过滤 `:PORT->` 否则会翻倍。

## 第二轮复查：连接监控的 bug 与性能

### 修掉的 bug

1. **`-D` 普通 HTTP 请求时上游连接没登记**。用户点「断开」只关掉客户端 socket，
   卡在 `http.ReadResponse` 上的 goroutine 会一直等一个可能永远不来的响应，
   SSH 通道跟着悬挂。已在 `forward_dynamic.go` 里加 `e.SetUpstream(remote)`。
2. **`Entry.closers` 可能无界增长**。`AddCloser` 是追加语义，动态转发里如果
   每轮 keep-alive 都追加一个上游连接，长连接跑几万次请求就挂着几万个已关闭对象。
   新增 `SetUpstream`：只保留最新一个上游连接，`KillWith` 时一并关闭。
   已加单测 `TestSetUpstreamReplacesInsteadOfAppending`。
3. **看门狗会在离开页面后把推送重新打开**。`Connections.vue` 的 `armWatchdog`
   在 `await ConnWatch(false)` 之后没重新检查 `mounted`，若此刻用户刚好切页，
   紧接着的 `ConnWatch(true)` 会让后端永久以 1Hz 采样 + 序列化 + 往死页面推事件。
   已在每个 await 之后重新检查，并在必要时补一次关闭。
4. **弹窗键盘不可用**。`DialogHost` 没有把焦点移进弹层，`@keydown.esc` 永远不触发。
   已加 `tabindex="-1"` + 打开时 focus，支持 Esc 取消、Enter 确定（焦点在卡片上时）。

## 第三轮：四个次要问题的确认与修复

全部确认存在，已修。

1. **剪贴板异常未捕获**。`copyCmd` / `copy` 只处理 `!ok`，`ClipboardSetText`
   reject（runtime 未就绪时 `window.runtime.X` 会同步抛 TypeError）就变成
   unhandled rejection，界面上什么都不显示。抽了 `lib/clipboard.ts` 的
   `copyText()`，统一收敛成 `false`，绝不抛。
2. **已关闭记录回收偏懒 + 持有连接引用**。`gcLocked` 原先只在 `Sample`
   （仅监控页打开时 1Hz）和 `Add` 达上限时跑；`Close()` 也不清 `closers`，
   正常关闭的记录一直挂着两个已关闭的 socket。现在：
   - `Close()` 顺手清 `closers` / `upstream`；
   - `Entry` 加 `reg` 反向引用，`Close`/`KillWith` 时 `noteClosed()`，
     按 `maxClosed` 摊薄（平均每 200 次关闭才跑一次 O(n) 清理）。
3. **速率首帧虚高**。`sample()` 现在按 `lastAt` 判断间隔，超过 `maxSampleGap`
   （3s）就只重建基准、速率归零。首轮采样同理——以前首轮直接把累计值当速率。

## 连接监控：修表头错位 + 全列排序

用户反馈两个问题（附截图）：表头「流量」「速率」和下面的数字不对齐；所有列都要能排序，
刷新数据后保持排序，默认打开不排序。

- 错位原因：表头是普通 `<span>`，默认左对齐；数值单元格是 `.cell.num {text-align: right}`。
  于是标题贴在列左边缘、数字贴在列右边缘，差了一整列宽。
  改成表头用 `<button class="th">`，数值列加 `.th.num {justify-content: flex-end}`，
  「时长」列也一并右对齐（`.cell.dur {text-align: right}`），三列口径统一。
- 排序：`sortKey` / `sortDir` 两个 ref，默认 `null` = 不排序（保持后端顺序，
  后端 `Registry.Snapshot` 本身按 `Started` 倒序，最新在前）。
  `sorted` 是 computed，依赖 `rows`，所以每次 1Hz 推送都会按当前列重排，不用额外监听。
- 三个实现要点：
  1. `Intl.Collator(undefined, {numeric: true})` 缓存在模块级——不然每次比较 new 一个，
     4096 行直接卡住；numeric 保证 `10.0.0.9` 排在 `10.0.0.103` 前面。
  2. 先 map 出排序键再 sort（decorate-sort-undecorate），比较函数里不再反复取字段、算时长。
  3. 只有按「时长」排时才读 `tick`，其它列不读 → 不会每秒白白重排 4096 行。
- 交互：点表头 → 该列默认方向（数值降序 / 文本升序）→ 再点反向 → 第三次取消排序。
  换顺序时把滚动位置归零（否则原位置指向的是别的行了）。
  箭头用 `order: -1` 放到文字左边，右对齐的列才能让文字右边缘与数字右边缘齐平；
  箭头固定占 9px，切换时表头文字不左右抖。
- 状态点列和操作列没做排序：状态有「全部/活动中/已关闭」三个 tab 已经能筛，
  16px 的列也放不下表头文字。
- 验证：临时用 `frontend/.preview/`（vite alias 把 `wailsjs/go/main/App` 和
  `wailsjs/runtime/runtime` 换成 mock，`window.__emit` 模拟后端推送）+ playwright-core 截图，

  推送后新数据自动重排。验证完目录已删除。

## 复查：又修掉两个 bug

**1. 滚动条占位导致表头与行错列（跨平台）**
`.tbody` 有滚动条、`.thead` 没有，两者共用同一套 grid 列宽。经典滚动条（Linux 的
WebKitGTK、旧版 WebView2、macOS 设了「始终显示滚动条」）会占掉 tbody 的内容宽度，
`1fr` 列先吃掉一点，后面的定宽列整体左移 —— 实测 15px 滚动条下偏移 `[0,0,-6,-15,-15,-15,-15]`。
修法：`measure()` 里读 `el.offsetWidth - el.clientWidth` 存进 `sbw`，表头
`:style="{paddingRight: 12 + sbw + 'px'}"` 让出同样宽度；用 `ResizeObserver` 盯 tbody，
列表从空到撑出滚动条（或反过来）时自动更新。实测 15px 下偏移全为 0，清空后回到 0。

**2. 速率是「每次采样的增量」而不是「每秒字节数」**
`sampleAt` 直接 `rateUp.Store(u - lastUp)`，隐含假设间隔恰好 1s。但 `connPump` 是
「采样 → 序列化 → 推送 → 等 ticker」，间隔恒大于 1s；ticker 漏拍（GC、休眠唤醒、前端卡顿）
时两秒的增量按一秒算，显示值翻倍虚高。`maxSampleGap` 只挡住 >3s 的情况。
改成 `perSecond(delta, elapsed) = delta * 1e9 / elapsed`（整数运算，delta 为负按 0）。
连带删掉了没人用的 `Entry.sample()`。
测试：`TestEntryCounters` / `TestSampleResetsAfterLongGap` 改用 `sampleAt` 显式指定时刻
（真实 `time.Now()` 连采两次间隔几微秒，会把 30 字节放大成天文数字）；
新增 `TestRateNormalizedByElapsed`（2 秒 1000 字节 = 500 B/s）。

**复查确认没问题的**：排序三态切换、切 tab / 搜索后排序保持、换排序时 scrollTop 归零、
删行后排序保持、空列表、快速连点表头、无 JS 异常（只有 favicon 404）。

## HTTP keep-alive 上游复用：实现了又还原（待用户决策）

## Windows 失败定位并修复：0 秒间隔上算不出速率

用户贴了 CI 日志，根因确认，而且**就是我这次改动引入的**（上一轮「不是本批改动引入」的
结论是错的，已更正 MEMORY.md）：

```
--- FAIL: TestConnectionTracking (0.08s)
conn_tracking_test.go:240: 进程识别成功: pid=9072 name="tunnel.test.exe"
conn_tracking_test.go:287: 活跃连接速率异常: upRate=0，期望 >= 4096
```

`upRate` 是**恰好 0**，不是偏小。归零路径只有三条（首轮基准 / `elapsed > 3s` / `elapsed <= 0`），
测试才 0.08 秒 → 只能是 `elapsed <= 0`。

**机制**：Windows 墙上时钟（`time.Now().UnixNano()`）粒度约 **15.6ms**，测试里两次
`reg.Sample()` 之间只隔一次 4KB 回环收发（几百微秒），落在**同一个 tick** → elapsed 正好 0。
改动前 `e.rateUp.Store(u - e.lastUp.Swap(u))` 直接存增量、不看 elapsed，所以能过；
我加了 `elapsed <= 0` 的除零保护，就把它丢进归零分支了。

**为什么之前一直没怀疑到这里**：先看到「4s 失败 == 4s 成功」就以为不是时间敏感，
其实 4s 是正常耗时，失败是**瞬间**发生的，两者并不矛盾。教训：**耗时相同只能排除
「等满超时」，排除不了「立即失败」**。

**修法**（不动生产代码：`app.go:170` 是唯一调用点、1Hz ticker，永远不会有 0 间隔）：
- `conn_tracking_test.go`：两次采样之间 `time.Sleep(100 * time.Millisecond)` 模拟 1Hz 节奏，
  让间隔在各平台都可测；断言改成 `UpRate > 0` + `Up >= len(big)`，不再钉具体数值
  （精确换算由 `conn` 包的 `TestRateNormalizedByElapsed` 用显式时刻覆盖）。
- 新增 `TestSampleSameInstantYieldsZeroRate`：把「0 间隔必须归零、不能除零崩、下一轮能恢复」
  这个契约钉住，防止以后有人删掉 `elapsed <= 0` 保护。

验证：`go vet ./...` 通过；`internal/conn` 四个速率用例全绿；
`internal/tunnel` `-count=5` 连跑五轮 ok（4.651s）。

**副产品**：日志里 `pid=9072 name="tunnel.test.exe"` 说明 `internal/proc` 的 Windows 实现
（`GetExtendedTcpTable` + `QueryFullProcessImageNameW`）**运行时确实可用**，
不再只有编译和 vet 证据。
